# 实验事实与叙事骨架（2026-10-28 夜）

**原则**：不为了让数字贴合开题报告而设计实验。指标服从实验，不反过来。
本文件只做一件事——把"现有的实验到底支持哪几句话"逐条钉死，每句都给出可复跑的证据；
支持不了的，明确列进"不能说的话"。

## 1. 今天新算出来的两个事实

### 1.1 本场景的"长度提升"上限由布设几何决定，等于 **1.2498**

做法：对每条真值，取两站局部航迹出现帧的**并集** / **较长单站**，即"任何算法最多能接出多长"。
结果（`results/_verify_report/ceiling.csv`）：

| 项 | 值 |
|---|---|
| 37 条真值的几何上限均值 | **1.2498** |
| 上限 > 1 的目标（真正可延长） | **29 条** |
| 上限恰为 1.000 的目标（两站覆盖互相包含） | **8 条** |

**这条改写了整个叙事**：契约里那条"复现上一版 1.250"从来不是算法指标，
它就是这个场景几何上限本身。上一版顶到 1.250 = 顶到天花板（100%），
现在的 1.234 = 天花板的 **98.7%**。

### 1.2 在线链路的"实现度" = 系统覆盖 / 几何并集 = **98.6%**

对 29 条可延长目标：

| 实现度 | 条数 | 说明 |
|---|---|---|
| ≥ 99% | **25 条** | 接力基本无损 |
| 95–99% | 3 条 | #16 98.2%、**#34 97.5%**、#37 98.9% |
| 90–95% | 1 条 | #10 94.2%（系统 65 / 并集 69） |
| < 90% | 0 条 | — |
| 均值 | **99.6%** | |

> 这一栏在 21:20 修掉一个合并方向 bug 后从 98.6% 升到 99.6%（#34 由 67.1% → 97.5%），
> 详见 §1.4。

8 条几何不可延长的目标，系统长度**恰好** 1.000（不是 0.98，也不是 1.02）——
这本身就是一次内部对照：**几何不给，算法不多给；几何给多少，算法吃多少。**

### 1.3 长度与融合覆盖是一对几何权衡（同代码、只改波束偏转）

| 布设 | 波束偏转 | 配对 | 融合覆盖率 | **长度比** | 共同帧融合 | 增益 | NEES(R1/R2) |
|---|---|---|---|---|---|---|---|
| 共视 | 0° | 37/37 | **70.9%** | **1.0096** | 8.385 km | +24.1% | 3.27 / 1.64 |
| 互补 | 4.6° | **37/37** | **19.8%** | **1.2460** | 7.929 km | +22.6% | 3.77 / 1.14 |

两条都跑同一份 `run.m`、同一场景、同一 seed 体系，只有 `coverage_tilt_deg` 不同（均为修复合并方向后的数字）。
注意 tilt=0 那行在修复前后**完全一致**——说明那个 bug 只在互补布设下才发作。

**这张表是整篇论文最值钱的一张**：它把"长度"和"融合"从"谁更强"变成"操作点在几何轴上的位置"——
- 两站看同一片天：几乎每帧都能融合（71%），融合增益最高（+24%），但**长度一点都长不了**（1.01）；
- 两站各看半程：长度长 23%，但只有 18% 的帧落在双源段，融合样本少 4 倍。
- 两者不可兼得。**想同时要，只能加站（三站以上），不是改算法。**

### 1.4 修掉的一个真 bug：合并方向被写死（#34 的真正死因）

**现象**：#34 CSZ9278 单站 47/55 帧、几何并集 79 帧，系统航迹只拿到 53 帧（0.964），
是唯一一条"越配越短"的航迹。

**诱因**：目标从南侧进入走廊，R2 先建系统航迹；等 R1 的局部航迹出现时，
门限/成熟度还没放行，于是另建了一条只持 R1 源的系统航迹。此后
`source_taken_by_other` 按设计堵死两条"互相认领"的路径，唯一出路是合并。

**根因**：`merge_duplicate_ct` 的"源是否还在"检查写死了方向——假设保留者持 R1、被合并者持 R2。
但保留者是"出生早的那条"，在覆盖互补布设里恰恰常是 R2 侧，于是
`find_local(L1, 0)` 恒为空 → `merge_cnt` 每帧清零 → 永不合并。

**证据（逐帧）**：两条航迹共存的 23 帧里，有 20 帧马氏 d² 在 0.01~3.7 之间，
远低于门限 5.99——**门限没问题，是合并这一步根本没走到判门限**。

**修复**：按保留者实际持有哪一站来查源（约 10 行，已留 `.bak`）；补了反向单测 T7
（R2 先建 CT）。原 T5 恰好构造的是"R1 先建"，所以这个方向从未被覆盖。

**效果**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 确认配对 | 36/37 | **37/37** |
| 长度比 | 1.2342 | **1.2460**（上限 1.2498 的 99.7%） |
| 延长 / 缩短 | 27 / 1 | **28 / 0** |
| #34 长度比 | 0.964 | **1.400** |
| 实现度均值 | 98.6% | **99.6%** |

> 这也说明：把"少配一对"当成"门限太紧"是错的——#14 是门限问题，#34 是合并方向问题，
> 两个目标两个病根。

## 3. 三条不能说的话（写进去会被问穿）

| 不能写 | 为什么 | 改写成 |
|---|---|---|
| "融合必然带来精度增益" | 默认模型集（0.7/1.5）下增益是 **−4.6%** | "增益符号由模型匹配度决定；匹配后 +20%" |
| "配准→关联→融合闭环已打通" | 跨区场景 `registration_mode='none'`，配准被显式关掉；第 2 章只能讲方法与近区（117–124°E）验证 | "本场景只考察时序与几何，配准留待独立标校集" |
| "虚假航迹率 0%" | 点迹由真值生成、点航关联是 oracle，结构上不可能产生虚假航迹 | "本实验不含杂波/虚警，虚假航迹率不作为考核项" |

另外两条口径必须写清分母：
- **长度比 1.234 是 37 条全体均值**；被延长的 27 条均值 1.322、最高 1.579；
- **配对 36/37**，查准 100%，漏的是 #34。

## 4. 叙事骨架（章节 → 用哪张表 → 说什么）

```
第 2 章  布设与几何
  ├─ 2.3 数据驱动场景（37 条 FR24 南北向航迹）
  ├─ 2.4 覆盖并集核算 → 几何上限 1.2498
  └─ 落点：把"1.25"定义成设计目标（几何决定的），而不是事后凑出来的结果

第 3 章  单站跟踪
  ├─ 两站各 ~60 帧覆盖，RMS 9.95 / 12.28 km
  └─ 如实报 NEES 3.77 / 1.14：协方差偏乐观，为第 4 章的门限失效埋下伏笔

第 4 章  跨站配对（本章最有信息量）
  ├─ 37/37，查准 100%（修复合并方向 bug 后）
  ├─ 三策略对比：dualgate 36、mewf 37（差的 #14 是硬门限问题）
  ├─ 机理 A：#14 逐帧轨迹 —— 硬门限同时掐死候选/建档/合并三条路径
  └─ 机理 B：#34 —— 合并保留者方向写死，已在 21:20 修复（§1.4）

第 5 章  融合
  ├─ 四算法（dualgate 配置）SCC 7.92 / BC 7.98 / CI 8.39 / FCI 8.12；mewf 配置 SCC 7.93
  ├─ ρ = 0.07~0.18 → BC≈SCC 是物理正确，不是没实现（删掉"真 BC"这个卖点）
  └─ 模型集敏感性：−4.6% → +20%（C5）

第 6 章  指标
  ├─ 长度：1.234 = 几何上限的 98.7%（先给上限，再给实现）
  ├─ 布设权衡表（1.3 节）：长度 ↔ 融合覆盖不可兼得
  └─ 指标 4（虚假航迹率）说明不适用
```

## 5. 还差什么（只有一件是必需的）

| 优先级 | 事项 | 目的 | 成本 |
|---|---|---|---|
| **必需** | 5~10 个 seed 的 MC，报 1.234 的均值±区间 | 回答"是不是这一个噪音实现运气好" | 每个 seed 约 90 s，随机流已修好，可直接跑 |
| 可选 | 协方差膨胀（按 NEES 缩放 P） | 把 #14 也拉回来，让 dualgate 也 37/37 | 动 `ukf/`，需回归全部实验 |
| 可选 | 一条目标"中途机动"的场景 | 证明在线性在机动下也成立 | 新场景 |

**结论**：故事已经能自圆其说，缺的只是误差条。不要再为 50% 设计任何实验。

## 6. 一句话

**"长度提升"的上限是布设给的（1.2498），在线链路拿到 98.6%；
融合的增益是模型集给的（匹配后 +20%）；
两者的此消彼长由波束偏转决定（0° 时 1.01/71%，4.6° 时 1.23/18%）。
这三句话全部有实验支撑，不需要任何一句去凑开题。**
